# 09. 회고

## 5일을 돌아보며

프로그램 시작 전 세운 목표는 "수상"이었습니다. 그런데 실제로 남은 것은 상장보다 **"성능 수치를 어떻게 다뤄야 하는가"** 에 대한 감각이었습니다.

---

## 배운 것

### 1. 좋은 숫자가 나왔을 때가 가장 위험하다

mAP 0.871이 나왔을 때 그대로 보고했다면 아무도 문제 제기를 하지 않았을 겁니다. 하지만 "650장이 전부 같은 영상에서 나왔는데 왜 vehicle이 0.96이지?"라는 의심 한 번이 전체 프로젝트의 성격을 바꿨습니다.

- 이미지 해시로 **near-duplicate 17%** 를 정량 검출
- 제공받은 사전학습 가중치가 **COCO가 아니라 같은 데이터셋에 이미 학습된 모델**임을 발견 (0스텝 성능 0.0009 vs 0.7638)
- 시퀀스 단위 재분할로 누수 **0%** 까지 교정
- 그리고 다시 확인 — **교정 후에도 성능은 거의 그대로였다(0.8714 → 0.8694)**

마지막 항목이 특히 중요했습니다. 의심했지만, **의심이 맞다고 결론을 정해두지 않았습니다.** 검증 결과 원래 수치가 방어 가능하다고 나왔고, 그 결과를 그대로 받아들였습니다.

### 2. 기각한 실험을 기록하면 그게 곧 발표 자료가 된다

TTA를 시도했다가 성능이 떨어졌을 때, 처음엔 실패로 여겼습니다. 그런데 **왜 떨어졌는지**를 파고들자(축소 패스에서 32px 미만 객체 소실) 그것이 "우리 데이터의 특성을 이해하고 있다"는 증거가 되었습니다.

> 채택한 실험은 결과를 보여주고, 기각한 실험은 **이해도를 보여줍니다.**

### 3. 병목을 먼저 측정하지 않으면 튜닝은 추측이다

라벨을 전수 파싱해 "pedestrian의 55%가 32px 미만"이라는 한 줄을 얻은 것이, 이후 모든 하이퍼파라미터 결정의 근거가 되었습니다. 이 측정 없이 imgsz를 올렸다면 운이 좋았을 뿐이고, 발표에서 "왜 1536인가"에 답하지 못했을 겁니다.

### 4. 사실 오류 하나가 전체 신뢰를 무너뜨린다

해커톤 발표 자료에서 "FMCW LiDAR는 안개를 투과한다"는 잘못된 주장을 발견하고 삭제했습니다. 심사위원이 연구원인 자리에서 이 문장 하나가 남아 있었다면 이후 모든 주장이 의심받았을 겁니다.

### 5. 모르는 것은 먼저 말하는 편이 낫다

미검증 항목 3가지를 먼저 공개하고 "이것이 1차 실증의 측정 목표"라고 제시했습니다. 숨기려 할수록 질문은 정확히 그곳으로 몰립니다.

## 놓친 것 · 아쉬운 것

솔직하게 남깁니다.

| 항목 | 내용 |
|---|---|
| **독립 테스트셋의 부재** | 650장이 전부 같은 주행 영상에서 나왔습니다. 시퀀스 재분할로 누수는 없앴지만, **다른 도로·다른 카메라에서의 일반화 성능은 끝내 측정하지 못했습니다.** 보고한 수치는 어디까지나 동일 도메인 내 성능입니다. |
| **변수 통제가 한 번 깨졌다** | `weight_decay` 실험에서 `workers`가 함께 바뀌어 augmentation 난수 스트림이 달라졌습니다. 개선폭(+1.60%p)이 노이즈의 1.8배라 채택은 했지만, **순수한 weight_decay 효과라고 단정할 수 없습니다.** |
| **누수를 더 일찍 확인했어야 했다** | 데이터 감사를 실습 중반에 했는데, **첫날에 했어야 할 일**이었습니다. 그 전까지의 튜닝 실험들은 오염된 기준선 위에서 측정된 것이라 일부 결론을 재검토해야 했습니다. |
| **행동 인식은 데모 수준에 머물렀다** | 도메인에 맞는 행동 클래스를 정의해 fine-tuning하는 단계까지 가지 못했고, Kinetics 사전학습 모델을 그대로 적용해 한계를 확인하는 데서 끝났습니다. |
| **CAN과 인지 파이프라인을 실제로 연결하지 못했다** | 개념적으로는 이해했지만, 검출 결과를 CAN 메시지로 내보내는 end-to-end 구현은 시간상 시도하지 못했습니다. |

## 프로그램 참여자에게 (다음 기수를 위해)

같은 프로그램을 준비하는 분들에게 도움이 될 만한 것만 추립니다.

1. **사전 준비의 최대 효과는 "여유"입니다.** Python·YOLO 실행을 미리 손에 익혀 가면 첫날부터 시간이 남고, 그 시간이 그대로 해커톤 준비 시간이 됩니다.
2. **완주가 1등 전략입니다.** 화려한 시도보다 `학습 → 평가 → 시각화`가 끝까지 돌아가는 파이프라인을 먼저 확보하세요. 마지막 날 완주 못 하는 팀이 실제로 나옵니다.
3. **중간 산출물을 계속 저장하세요.** 학습 그래프, mAP 수치, 검출 결과 이미지 — 이게 그대로 발표 자료가 됩니다.
4. **수요일부터 해커톤을 의식하세요.** 목요일 밤에 시작하는 팀과 격차가 큽니다.
5. **데이터부터 의심하세요.** 특히 주행 영상에서 추출한 데이터셋의 무작위 분할은 거의 항상 누수를 포함합니다.
